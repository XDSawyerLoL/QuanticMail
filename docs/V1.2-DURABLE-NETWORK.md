# QuanticMail V1.2 — Durable Network

QuanticMail V1.2 strengthens device routing identifiers and makes V1.1 protocol state durable on the standalone Quantic Relay.

## What is durable now

A standalone relay writes one atomic `relay-state.json` containing:

- registered Quantic identities and aliases,
- authorized devices and auth-token hashes,
- encrypted message queues,
- delivery receipts,
- signed identity manifests,
- available signed one-time prekeys,
- consumed prekey tombstones.

The file is written through a temporary owner-only file, fsynced, then atomically renamed. A failed save rolls the in-memory mutation back to the previous snapshot.

Pairing rendezvous remain deliberately ephemeral. They contain short-lived association secrets and expire after ten minutes; they are not written to durable relay state.

## State format V2

`quantic-relay-state` version 2 adds:

- `manifests`
- `preKeyPools`
- `consumedPreKeys`

Version 1 state files are still accepted. They are restored with empty V1.1 stores and become version 2 on the next save. Unknown future versions and corrupt JSON are rejected instead of silently resetting the relay.

## Strong device identifiers

New devices use:

```text
d-<32 lowercase hexadecimal characters>
```

The 32 hexadecimal characters are the first 128 bits of SHA-256 over:

```text
P-256:<public x>:<public y>
```

Existing `d-<10 hex>` device IDs remain valid. A certificate or manifest is accepted only when the supplied 10- or 32-hex prefix actually matches the full device public key digest.

Already-issued certificates are never rewritten just to lengthen the device ID.

## Standalone V1.1 protocol routes

The standalone relay now serves:

```text
GET  /api/quantic/manifest
POST /api/quantic/manifest
POST /api/quantic/devices/revoke
POST /api/quantic/prekeys/publish
POST /api/quantic/prekeys/claim
GET  /api/quantic/prekeys/status
```

alongside the existing identity, device, send, pull, acknowledgement, receipt and health routes.

`GET /api/quantic/health` advertises durable-state/manifests/prekeys capabilities.

## Prekey durability

One-time prekeys remain public signed records on the relay; their private halves stay in the browser IndexedDB only.

A claimed prekey is removed from the available pool and a tombstone is persisted until the prekey expiry time. Restarting the relay therefore cannot make a consumed prekey available again.

## Multi-relay routing

The browser's global Quantic fetch interceptor sends `/api/quantic/*` requests through the configured relay list and remembers the active relay.

404 failover is enabled only where a 404 can mean that an older relay does not implement a capability, including pairing, manifests, registry status and prekey publication/status. A one-time prekey claim returning 404 is **not** retried on another relay because that response can legitimately mean that the pool is empty.

Pairing may therefore continue through the public bootstrap relay even when a local standalone relay is active.

## Optional GitHub identity checkpoint

GitHub is optional and stores **signed identity manifests only**. It never stores message plaintext or private keys.

Environment variables:

```text
QUANTIC_GITHUB_TOKEN=<fine-grained token>
QUANTIC_GITHUB_OWNER=XDSawyerLoL
QUANTIC_GITHUB_REPO=QuanticMail
QUANTIC_GITHUB_BRANCH=registry
```

The token should be restricted to the QuanticMail repository with `Contents: Read and write` only.

Registry paths are derived from a SHA-256 hash of the canonical address. V1.2 also removes the canonical address from Git commit messages; checkpoint messages expose only a shortened path hash and the manifest sequence.

If the token is absent, `/api/quantic/registry/status` reports memory mode. This does not affect the standalone relay's local disk durability.

## Deployment model

A practical free deployment is:

```text
Browser / PC A       Browser / PC B
      |                    |
      +---- local relay ----+
             |
       relay-state.json

Render = public bootstrap / web client
GitHub = optional signed identity checkpoint
```

The standalone relay is the durable owner of encrypted message transport state. Render does not need to be the sole durable message store.

## Security boundary

V1.2 does not turn QuanticMail into a formally audited cryptographic protocol. It preserves the V1.1 P-256/AES-GCM design and one-time-prekey forward-secrecy improvement. It does not implement a full Double Ratchet.
