# Quantic Pay — remote witness transport laboratory (not a real payment rail)

The fixed-roster 3/4 anti-rollback witnesses can now communicate through
**mutually authenticated TLS 1.3**. This is a laboratory implementation that
lets each witness own its SQLite fence and Ed25519 + ML-DSA-65 private keys
inside **its own Node process**. The orchestrator needs only its separate
TLS client key/certificate, never the witnesses' signing keys.

This does not create four independent operators, physical hosts, or legal
payment infrastructure. The CI test starts four distinct processes on **one
GitHub Actions machine** to prove process/RPC isolation, not geographical
redundancy.

## Trust boundaries

- Each witness process starts from
  `scripts/quantic-pay-witness-node-lab.mjs` with an explicitly provisioned
  private JSON configuration at the absolute path
  `QUANTIC_PAY_WITNESS_CONFIG`.
- The witness owns its independent, persistent SQLite directory, Ed25519
  private signing key, ML-DSA-65 private signing key, TLS server key and cert.
- The private config, private keys and certificates must be regular files
  owned by the process account, mode **0600 on Unix**, with no symlinks.
- Each server has a CA-trusted TLS server certificate with the correct
  DNS/IP SAN and **a distinct SHA-256 DER certificate pin** configured at
  the client. The server separately allowlists the orchestrator's TLS client
  certificate fingerprint (SHA-256 of DER). TLS 1.3 is mandatory.
- Operators must provision these CA certificates and permissions
  independently. No CA credentials are generated by the runtime.
- The server accepts only four JSON operations on `POST /v1/witness`:
  `status`, `attest`, `grantCertified`, and `complete`.
- `grantCertified` re-verifies the real **11/16 hybrid certified shard
  checkpoint** with the witness's locally installed ledger verifier **before
  its durable vote lock**. A bad but mutually authenticated caller cannot
  lock a witness using an uncertified proposal.
- Three different witness identities must sign the same request. The
  orchestrator independently checks their Ed25519 and ML-DSA-65 signatures;
  successful TLS alone is never sufficient.
- The four nodes retain independent persistent antirollback data. If three
  nodes are offline, halted, or rolled back, this 3/4 quorum fails closed.
- A CA certificate file and pin are both mandatory: no `rejectUnauthorized:
  false`, no insecure localhost bypass.

### Private witness configuration example

Store the following JSON in a protected file owned by that witness's
dedicated OS account (placeholders only):

```json
{
  "config": {"shards": [], "wallets": []},
  "options": {"reservationsEnabled": true, "crossShardAtomicEnabled": true, "inboundPreparationEnabled": true},
  "shard": "demo-east",
  "witnesses": [],
  "credentials": {
    "pin": "<64-lowercase-hex>",
    "classicalKeyPath": "/private/witness/ed25519.pkcs8.pem",
    "pqKeyPath": "/private/witness/mldsa65.pkcs8.pem"
  },
  "identity": {
    "keyPath": "/private/witness/tls-server.key",
    "certPath": "/private/witness/tls-server.crt",
    "caPath": "/private/witness/trusted-controller-ca.crt"
  },
  "directory": "/private/witness/fence",
  "createNew": false,
  "host": "127.0.0.1",
  "port": 9443,
  "allowedClientCertPins": ["<64-lowercase-hex>"]
}
```

The `config.shards`, `config.wallets`, and `witnesses` lists above
**are deliberately empty placeholders**; copy the actual, independently
reviewed public roster and network definitions from a trusted local
configuration. This example cannot start a witness as-is.

On a remote test host, bind to an operator-provisioned interface rather than
the loopback default, and configure firewall rules so only the intended
orchestrator can reach TCP 9443. Keep private keys local on each host.
Never expose this RPC directly to the public Internet.

```bash
chmod 600 /private/witness/config.json /private/witness/*.pem /private/witness/*.key
export QUANTIC_PAY_WITNESS_CONFIG=/private/witness/config.json
node scripts/quantic-pay-witness-node-lab.mjs
```

For an initial lab only, `createNew:true` provisions a new SQLite fence.
**Never use it when restoring an existing witness**: the existing journal
must be reopened, and a lagging node must verify a freshly attested 3/4
checkpoint and the full intervening certified block sequence. The separate
offline catch-up adapter remains local; remote repair over mTLS is not yet
implemented.

### Coordinator

Use `openPayWitnessMtlsClientLab({url,credentials,serverCertPin})` once for
each of the four hosts. Supply the resulting four clients and the four
**public** witness pins to
`openRemoteShardWitnessCoordinatorLab({config,options,shard,witnesses,clients})`.

The coordinator exposes asynchronous `fresh(target)`,
`publishCheckpoint(checkpoint)`, `synchronize(replica)`, and
`statuses()`. No witness signing key is transmitted to the coordinator.
The existing synchronous recovery worker still uses an in-process bridge:
**remote coordinator integration with the continuous cross-shard worker is
a separate pending step**. Do not claim autonomous multi-host recovery yet.

### Validation criteria

`tests/pay-remote-witness-mtls.test.mjs` provisions a test CA and distinct
TLS server certs with OpenSSL, then starts four separate Node witness
processes on loopback with distinct SQLite journals and post-quantum private
keys. The test must confirm: good mTLS traffic; rejection of an intruder
whose client certificate is signed by the same CA but not allowlisted;
rejection of a wrong server pin; refusal of an uncertified vote **without a
durable lock**; and loss of liveness at 2/4 while retaining liveness at 3/4.

All currencies and transfers remain simulated. No euro numérique,
regulatory authorisation, commercial high-availability SLA, secure hardware
custody or remote physical failure domain is provided.
