# QuanticMail V0.3 — Production mail server

## Production topology

QuanticMail deliberately separates the public webmail application from the SMTP/JMAP mail core.

- Web application: `https://quanticmail.onrender.com`
- Mail domain: a domain owned and controlled by Quantic Sillage
- Mail server hostname: a dedicated subdomain such as `mx.example.com`
- Mail core: Stalwart on a dedicated Linux VPS
- VPS PTR/rDNS: points the public VPS IP back to the Stalwart hostname

The current brand-domain candidate is `quanticsillage.com`, but production DNS must not be published until the domain has actually been purchased and is under Quantic Sillage control.

`Sillage.com` is not a production target: it is already registered and used outside this project.

## Required infrastructure

The Stalwart VPS should provide:

- Ubuntu LTS or another supported Linux distribution
- dedicated public IPv4 address
- persistent storage
- TCP 25 open inbound and outbound for server-to-server SMTP
- TCP 443 open for Stalwart HTTPS/JMAP
- TCP 465 and 587 open for authenticated submission
- TCP 993 open for IMAPS compatibility
- TCP 4190 optional for ManageSieve
- ability to configure reverse DNS / PTR
- firewall default-deny for unrelated inbound ports

A conventional web/serverless platform is not a substitute for the mail core because reliable mail delivery needs SMTP listeners and reverse DNS control.

## Bootstrap the VPS

From the repository root on a fresh Ubuntu VPS:

```bash
sudo env MAIL_SERVER_HOSTNAME=mx.example.com bash scripts/bootstrap-mail-vps.sh
```

The bootstrap script:

1. installs Docker Engine and Docker Compose,
2. enables UFW,
3. opens the required mail/TLS ports,
4. copies the production Compose file to `/opt/quanticmail`,
5. stores only the public mail hostname in `/opt/quanticmail/.env`,
6. validates the Compose configuration,
7. starts Stalwart,
8. prints the temporary Stalwart bootstrap administrator credentials.

The bootstrap admin HTTP listener is bound to `127.0.0.1:8080`, not the public interface. Reach it using an SSH tunnel:

```bash
ssh -L 8080:127.0.0.1:8080 root@SERVER_IP
```

Then open `http://127.0.0.1:8080/admin` locally.

## Stalwart first-run values

Use the setup wizard with:

- Server hostname: the value of `MAIL_SERVER_HOSTNAME`
- Default email domain: the domain owned by Quantic Sillage
- Automatic TLS: enabled
- DKIM generation: enabled
- Storage: local/RocksDB for the first single-node deployment
- Directory: internal directory for the first production version
- DNS management: manual initially, or a supported automatic DNS provider later
- Logging: console in Docker

After the wizard completes, restart Stalwart and use HTTPS for administration.

## DNS order of operations

Do not publish the MX record first. Bring the mail host online in this order:

1. Create the mail-host `A` record pointing to the VPS IPv4 address.
2. Confirm the hostname resolves publicly.
3. Configure the VPS provider PTR/rDNS to point that IPv4 address back to the exact same mail hostname.
4. Confirm forward-confirmed reverse DNS in both directions.
5. Complete Stalwart setup and generate DKIM keys.
6. Retrieve Stalwart's generated DNS zone file.
7. Publish MX, SPF, DKIM, DMARC and the generated discovery/security records.
8. Verify propagation and TLS.
9. Create the first production mailbox.
10. Run external inbound/outbound delivery tests.

Stalwart's generated zone file is the source of truth for DKIM selectors and its final recommended DNS records.

## Starter DNS shape

For an owned domain `example.com` and mail host `mx.example.com`:

```dns
mx.example.com.              A       VPS_IP
example.com.                 MX 10   mx.example.com.
example.com.                 TXT     "v=spf1 mx -all"
_dmarc.example.com.          TXT     "v=DMARC1; p=none; rua=mailto:dmarc@example.com; adkim=s; aspf=s"
```

Do not invent DKIM public keys. Publish the selectors and public keys generated by Stalwart.

Start DMARC in monitoring mode while validating the system. Tighten the policy only after SPF/DKIM alignment and legitimate sending sources are confirmed.

## First mailbox

Once the real mail domain is owned and provisioned, create the first account in Stalwart. For the current brand-domain candidate that would be:

```text
valentin.hernandez@quanticsillage.com
```

Use a unique high-entropy password. Never store mailbox passwords, administrator passwords, DKIM private keys or TLS private keys in GitHub.

## QuanticMail web configuration

The deployed Next.js application needs:

```env
NEXT_PUBLIC_APP_NAME=QuanticMail
NEXT_PUBLIC_MAIL_DOMAIN=<owned-domain>
JMAP_SESSION_URL=https://<mail-hostname>/.well-known/jmap
SESSION_SECRET=<production secret, 32+ random bytes>
```

The Render service already exists. The JMAP endpoint will become functional as soon as the Stalwart host and DNS are live.

## Hostinger VPS option

Hostinger VPS can be used for the first mail node. Hostinger documents that VPS users can configure PTR/rDNS in hPanel after the domain's A record points to the VPS, and currently states that SMTP port 25 is not blocked. Hostinger also enforces a sending limit of about five messages per minute on VPS SMTP traffic, which is suitable for an initial corporate mailbox but not bulk mail.

## Production validation checklist

Before sending real business mail:

1. Mail hostname resolves to the dedicated VPS IPv4.
2. PTR resolves the VPS IPv4 back to the same mail hostname.
3. TLS certificate is valid for the mail hostname.
4. JMAP discovery works over HTTPS.
5. SMTP 25 is externally reachable.
6. Submission on 465/587 requires authentication and TLS.
7. IMAPS 993 works if third-party clients are supported.
8. MX points only to active mail servers.
9. SPF passes.
10. DKIM passes with the Stalwart-generated selector.
11. DMARC alignment passes.
12. The server is not an open relay.
13. Outbound mail reaches Gmail, Outlook and Proton Mail without authentication failures.
14. Inbound mail from external providers reaches the QuanticMail mailbox.
15. Stalwart persistent volumes are backed up.
