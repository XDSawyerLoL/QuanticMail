# Quantic Network V0.6 — Durable local delivery

V0.6 keeps the zero-cost Render relay but changes the delivery contract so the relay is no longer the only place holding an undelivered message.

## Delivery lifecycle

1. The sender resolves the recipient's `name@quantic` identity.
2. On first contact, the recipient public key is pinned in local IndexedDB.
3. The message is encrypted in the sender browser with ECDH P-256 and AES-256-GCM.
4. The plaintext sent copy is stored locally and the encrypted envelope is written to the local outbox.
5. The client submits the encrypted envelope to Render.
6. Repeated submissions of the same client message ID are deduplicated while the relay process is alive.
7. The recipient pulls the envelope, decrypts it and stores the readable message locally.
8. Only after local recipient persistence succeeds does the recipient acknowledge the relay envelope.
9. The relay creates a delivery receipt for the original sender.
10. The sender removes the encrypted local outbox item only after receiving that delivery receipt.

If a relay request fails, the encrypted outbox item remains on the sender device and is retried automatically.

## Contact key pinning

The first successfully resolved public key for a contact is saved locally. Future successful directory resolutions must return the same P-256 public key. A silent key change blocks sending and displays a security error instead of automatically trusting the replacement key.

If the directory is temporarily unavailable but the contact is already known, QuanticMail can encrypt a new message with the locally pinned public key.

This is a trust-on-first-use model. It protects established relationships from silent key replacement, but it does not yet provide a globally authoritative first-contact identity proof.

## Render restart behavior

Render Free web services have an ephemeral process/filesystem. A restart can clear:

- current in-memory handle registrations;
- encrypted envelopes currently waiting only in the relay;
- delivery receipts not yet collected.

V0.6 mitigates message loss by retaining each encrypted outbound envelope on the sender device until a receipt is collected. After a restart, an active sender can re-register its identity and resubmit pending envelopes. The recipient's local database deduplicates the readable message by the client message ID.

The remaining unsolved infrastructure problem is permanent global ownership of a human-readable handle such as `vnhz@quantic` without introducing a paid central database. That should be treated separately from message durability.

## Security boundary

Render sees routing metadata (`from`, `to`, timestamps and message IDs) plus ciphertext and ephemeral public keys. It does not receive the plaintext subject or body in the Quantic Network flow.

Private identity keys remain in browser IndexedDB and are never sent to Render.
