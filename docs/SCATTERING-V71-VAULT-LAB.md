# Scattering V7.1: first Identity Vault integration boundary (laboratory only)

The current vault exports private identity keys under password-derived AES-GCM (PBKDF2-SHA256, 250,000 iterations, see lib/quantic/vault.ts), while the native V7.1 pacer consumes QS69Q001 encrypted batches. This isolated Node-side handoff validates the existing binary batch format and publishes it atomically to a separate scattering-lab directory. No changes to vault.ts, production transport, identity signing, authentication, or account login. No automatically started process. No real keys or user data are permitted in this trial.

Run node --test tests/scattering-lab-spool.test.mjs. A harness can call publishLabSpool with labOnly:true, source (a synthetic V7.1 Java-produced batch) and queueRoot (a private local directory); launch native pacer with --queue-dir pointing at queueRoot/scattering-lab, using the separately obtained V7.1 laboratory binaries and localhost only. This module does not install, launch, or verify the native binary. A .ready batch is never a delivery receipt.

Security boundaries: SHA-256 is only an accidental-corruption check. It does not prevent a privileged local writer from replacing/replaying a batch. The current V7.1 receiver only deduplicates in memory; production requires durable authenticated anti-replay and key epochs. Windows ACLs, integrity of the installed binaries, allowed peers, authenticated key agreement, key rotation, native IPC authentication, fragmentation/reassembly, bounded queues and independent physical-network tests are prerequisites. Never derive the scattering key from root credentials. Do not claim historical or real-world attack probabilities from a tag length or packet-loss rate. No confidential traffic or production fallback to ordinary transport without an explicit policy decision.
