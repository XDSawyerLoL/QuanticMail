# Quantic Pay — isolated laboratory v0.1
Shared local simulator for /pay (static Hostinger /mail/pay/) and packaged Windows dashboard. Explicit fictional recipients, integer cents, prepare/confirm/cancel/expiry, duplicate confirmation without second debit, test-only history in memory. No network, banking identifiers, real money, redemption, payment token, wallet keys or claim of official compatibility. No code changes to Identity Vault or Quantic Mail transport. A simulation receipt is not evidence of payment. Future work: define a PSP integration boundary and compare official pilot candidate ISO 20022/API/CPACE specifications, establish regulated partner, implement authorization with applicable SCA and financial-purpose binding separately from mail signatures, independent transaction integrity/reconciliation, privacy and audit. The BCE pilot FAQ (updated 28 October 2026) describes technical service providers supporting participating PSPs, with PSP responsibility: https://www.ecb.europa.eu/euro/digital_euro/pilot/html/ecb.faq-digital-euro-pilot.en.html. No participation or approval currently established.

V0.2: the local Windows simulation now creates fresh ephemeral P-256 and ML-DSA-65 demonstration signing keys using bundled Node 24. A separate payment-simulation domain binds the session, key pins, exact fictional payee and cents, intent ID, currency, expiry and random challenge. Explicit consent, both signature verifications and single consumption precede the simulated debit. Negative tests modify the amount, payee, currency, expiry and signatures, try another session and repeat consumption. The browser remains the simple unsigned simulator. No production Identity Vault access, financial certificate, persistent financial ledger, real PSP integration or real money. Keys and proof state are process-local; no guarantee against compromised process or physical custody attack. Do not treat this as strong customer authentication or digital euro compliance.

V0.3 experimental Windows Pay-only vault: dedicated encrypted P-256 and ML-DSA-65 private keys, separate magic, PBKDF2/AES-GCM using existing native vault primitives and protected Windows directories/files. Create a new directory only; independent public pins required to unlock; actual console passphrase and exact fictional amount/recipient approval. Native proof contains only public keys and signatures in the separate simulation domain. The client independently checks both signatures, nonce, amount, expiry and pins before its in-memory simulated debit. No shared mail/identity keys, no registry enrollment, no payment processing, no durable payment ledger or cross-session replay protection. Windows automated test covers storage reopening, wrong password/pin, ciphertext damage, altered amount and refused/expired operations; operator terminal workflow and physical test remain required.

V0.4 first increment: fix the missing standard-library P-256 scalar reopening helper, then write a private exclusive nonce-named synthetic proof record and verify exact readback before returning the proof. Duplicate nonce record refuses release, including after reopening the process, while the directory is intact. Record contains public signatures and fictional payment metadata, not private keys. Partial files are retained and fail closed. This is not a balance ledger, not encrypted transaction metadata, and not rollback resistance against an adversary able to delete or restore the directory. Do not assume settlement or successful receipt delivery. Tests check duplicate refusal and retained exact bytes. Scattering integration still pending.

V0.4 second increment: read-only synthetic proof-set reconciliation. Verify each historical P-256 + ML-DSA-65 signature against independently pinned Pay keys, canonical nonce-sorted commitment, reject duplicate nonces, then compare count and digest against at least three matching independently pinned Ed25519 checkpoint votes from four distinct witnesses. Fresh unpredictable request nonce and 15-second expiry prevent old response reuse. Each issuer must maintain its own independently retained proof set; the included test models four witnesses in one process, not deployed independent services. Detect deletion, altered proofs, conflicting votes and stale responses when witnesses actually hold current history. This module is not yet wired into the native confirmation path, does not provide financial settlement, persistent witness custody, rollback-proof storage on its own or certified SCA. Real-money authorization always false.

V0.4 third increment: separate local quorum simulation workflow, accessible in the Windows dashboard. The new flow checks a fresh 3/4 proof-set quorum before requesting the two test signatures, verifies the exact candidate intent and nonce, submits it to witnesses and requires a second fresh matching quorum over the old set plus the candidate before reducing the fictional balance. Any failure once the operation starts locks the session, with no automatic retry. The demo has ephemeral Pay keys and four separately held in-memory witness states; it is NOT the native Pay vault path, persistent independent authority deployment, consensus or atomic commit. Tests cover two successful three-witness transactions, pre/post quorum insufficiency and 2/2 split. Existing local native-vault simulation remains separate and is not quorum-protected. Real payment and settlement flags always false.

V0.4 fourth increment: an explicit Windows dashboard operation creates a NEW dedicated native Pay vault using the verified native executable, then supplies its actual console-gated dual-signature operation as the signer of the before/after local quorum flow. The callback does not generate ephemeral replacement Pay keys. Native receipts persist; four witness states and witness keys are still ephemeral, all on the same machine. The native provisioning command refuses any existing directory, so this specific mode cannot silently reinitialize an old vault into empty witnesses. Closing the session ends the experiment permanently for that directory. No direct fallback on signing failure, no real payment, no remote or durable witnesses, no complete anti-rollback guarantee, no Scattering yet. CI checks callback failure/pre-quorum behavior and packaged script syntax; real interactive execution requires a Windows console and manual approval. Existing stand-alone simulation modes remain separate.

V0.4 fifth increment: explicitly selected pay-lab Scattering profile with only checkpoint and submit operations, separate HTTP route allowlist and HKDF domain separating carrier keys from mailbox traffic. Existing mailbox profile remains default with unchanged key derivation. The new client accepts only a loopback carrier port, bounded JSON and an explicit laboratory bearer token; no direct HTTP fallback. Linux CI now runs a native UDP test using two pacers and two sinks, a fresh Pay epoch and a loopback fixture holding four test witness states. It carries both fresh quorum requests and the hybrid-signed fictional proof; checks rejection of mail routes and transport loss without a further debit. This fixture signs in Node, not the native Windows vault. No deployed remote authorities, persistent financial storage, physical-network measurement, production PSP connectivity or real payment. The Windows native vault + quorum mode remains local and separate. Reusing an epoch across profiles is not supported.

V0.4 sixth increment: native Pay UDP test moved to the existing pinned Node 24 CI job because the Debian native container's Node runtime lacks ML-DSA-65. No classical fallback. Add a Linux-only private SQLite witness store, explicit new directory provisioning, independently supplied Ed25519 key/pin, immutable nonce uniqueness, full synchronous SQLite transactions, exact prior root/count checks, re-verification of historical hybrid signatures and bounded synthetic balance. Reopening never intentionally creates an absent store. The UDP test now uses four separate witness databases and closes/reopens each after appending before the post-quorum request. Unit tests check restart, stale root, duplicate, wrong key, missing store and overdraft refusal. All four stores are still on one CI host; key custody is externally supplied, no remote service, no distributed atomic commit and no protection against rollback of all witness databases together. No real funds, no production use.
