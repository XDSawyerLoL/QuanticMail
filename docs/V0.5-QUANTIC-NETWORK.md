# QuanticMail V0.5 — Quantic Network

QuanticMail V0.5 no longer uses email as the core transport.

## Core model

- human-readable identities such as `vnhz@quantic`
- ECDH P-256 identity keys generated on the device
- public keys published to the Quantic directory
- private keys kept locally
- AES-GCM message encryption before content leaves the sender device
- Render acts as directory and temporary encrypted relay, not as the mailbox
- decrypted messages are stored in the browser's IndexedDB on the recipient device

## Protocol alpha

1. The user chooses a handle.
2. The client generates an ECDH P-256 key pair and a random device token.
3. The client registers the handle, public key and hashed device credential with the Render relay.
4. A sender resolves the recipient's public key.
5. The sender generates an ephemeral ECDH key pair, derives an AES-256-GCM key, and encrypts the payload locally.
6. Render queues only the encrypted envelope and routing metadata.
7. The recipient polls the relay, derives the same AES key with its private key, decrypts locally and stores the readable message in IndexedDB.
8. The client acknowledges the relay envelope only after the local save succeeds.

## What Render can see

The alpha relay can see routing metadata: sender identity, recipient identity, timestamps, ciphertext size and the temporary encrypted envelope. It does not need the plaintext message or the recipient private key.

## Current alpha limitation

The directory and relay queue are process-local in V0.5 alpha. A Render restart or redeploy can clear identity reservations and pending envelopes. Local decrypted mail remains on the user's device. Durable zero-cost relay persistence is the next infrastructure step.

## Not SMTP email

`name@quantic` is a Quantic Network identity, not a standard SMTP address. The network does not require MX, IMAP, SMTP, SPF, DKIM, DMARC, a phone number or a purchased domain. External email gateways may be added later without making the Quantic Network depend on them.
