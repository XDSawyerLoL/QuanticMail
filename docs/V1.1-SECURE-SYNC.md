# QuanticMail V1.1 — Secure Sync

V1.1 hardens Quantic identity locators, introduces signed one-time prekeys, replaces manual device pairing as the primary UX with an encrypted QR rendezvous, and synchronizes sent history to the user's other authorized devices.

## 1. Canonical identity hardening

New identities derive a 32-hex-character (128-bit displayed) fingerprint from SHA-256 of the ECDSA P-256 master signing public key.

Example:

```text
sansa~0123456789abcdef0123456789abcdef@quantic
```

Legacy 10-hex canonical identities remain accepted. A stored legacy identity is never silently rewritten to a longer locator. When registering or recovering, the server checks that the requested 10- or 32-hex fingerprint is the exact prefix derived from the supplied signing public key.

## 2. Device trust model

The root device holds the identity master signing private key. Every linked device generates locally:

- an ECDH P-256 encryption key pair;
- an ECDSA P-256 device-signing key pair;
- a random device auth token.

The root signs a device certificate. The signed identity manifest is the current authorization set and contains a monotonically increasing sequence number. A later manifest cannot reactivate an already-revoked device or discard revocation history.

## 3. One-time prekeys

Each active device maintains a pool of one-time ECDH P-256 keys. The private half is stored only in that device's IndexedDB.

A public prekey record contains:

```text
version
canonicalAddress
deviceId
preKeyId
publicKey
createdAt
expiresAt
signature
```

The record is signed by the device-signing key. The relay checks the signature against the device key in the current signed manifest before accepting the record.

### Pool policy

- target pool: 32 records;
- replenish when relay availability drops below 12;
- relay maximum: 64 records per device;
- default client prekey lifetime: 7 days;
- claim is atomic;
- a claimed prekey receives a server-side tombstone until its expiry and cannot be republished in that relay process.

Relay prekey memory is intentionally not described as durable. After a Render restart, a device creates fresh records as required.

## 4. Message envelope compatibility

V1.1 keeps the existing V1 relay envelope shape. The one-time prekey identifier is carried in the standard JWK `kid` field of the sender's ephemeral ECDH public key:

```text
quantic-prekey:<32-hex-preKeyId>
```

If that marker exists, the recipient must decrypt with the matching private one-time prekey. If it does not exist, the envelope is treated as a static-key fallback/legacy V1 delivery.

A one-time prekey private key is deleted only after:

1. AES-GCM authenticated decryption succeeds;
2. payload/transport semantics validate;
3. the readable message is persisted locally.

The relay envelope is then acknowledged.

## 5. QR pairing

The root device creates a random 32-byte secret and a 10-minute pairing invitation.

The QR URL is shaped as:

```text
https://<quantic-host>/devices?pair=<invite-id>#secret=<base64url-secret>
```

The secret stays in the URL fragment. Browser HTTP navigation does not include the fragment in the request target.

### New-device flow

1. New device scans the QR.
2. It generates independent encryption/signing keys locally.
3. It posts a public device request to the temporary rendezvous.
4. Root device sees the request and explicitly approves it.
5. Root signs the device certificate and an incremented manifest.
6. Root builds a bootstrap package with certificate, manifest and locally available message history.
7. Package is encrypted with HKDF-SHA-256 + AES-256-GCM using the pairing secret.
8. New device retrieves the encrypted package once, decrypts locally and verifies all signatures before installation.

The encrypted pairing package is capped at 4 MiB. If the local history is too large, the root progressively reduces the copied history and marks the bootstrap as partial.

Manual file pairing remains available at `/devices/files` as a fallback.

## 6. Sent-history synchronization

Every logical outgoing message receives a stable logical message ID.

For the external recipient, QuanticMail creates one transport delivery per active recipient device. For the sender's other active devices, QuanticMail creates encrypted `syncCopy` deliveries transported back to the sender's canonical identity.

A sync payload keeps:

- `from`: sender canonical identity;
- `to`: external logical recipient;
- `syncCopy: true`.

The transport envelope itself has both sender and transport recipient equal to the sender identity. The receiving device validates that relation before storing the record as `direction: "out"`.

This separates logical mail history from relay routing metadata while allowing every authorized device to build the same sent folder.

## 7. Local durability

IndexedDB version 6 stores:

- current local identity;
- readable local messages;
- contact/key pins;
- encrypted outbox deliveries;
- pairing pending state;
- local one-time prekeys.

The outbox stores already-encrypted device deliveries. Retry does not claim a second prekey: the exact encrypted delivery is retried until its delivery receipt arrives.

Pairing history imports and ongoing sync copies are idempotent because local messages are keyed by the stable logical message ID.

## 8. Optional GitHub manifest registry

The repository includes a `registry` branch. Signed manifests can be checkpointed there when these Render runtime variables are configured:

```text
QUANTIC_GITHUB_TOKEN=<write-capable repository token>
QUANTIC_GITHUB_OWNER=XDSawyerLoL
QUANTIC_GITHUB_REPO=QuanticMail
QUANTIC_GITHUB_BRANCH=registry
```

Only signed public manifest state is written. No private keys, auth tokens, pairing secrets or message plaintext belong in the registry.

Without `QUANTIC_GITHUB_TOKEN`, runtime status explicitly reports memory mode. That is a deliberate degraded mode, not durable persistence.

## 9. Security properties and non-claims

V1.1 provides:

- self-certifying identity locators;
- root-controlled device authorization/revocation;
- signed monotonic device manifests;
- independent per-device encryption keys;
- signed one-time public prekeys with atomic relay claim;
- encrypted QR bootstrap;
- local-first readable storage;
- encrypted durable client outbox.

V1.1 does **not** claim:

- a formally proven protocol;
- a third-party security audit;
- durable server-side message queues on Render Free;
- Signal-style Double Ratchet sessions;
- uniform forward secrecy when static fallback is used;
- protection after compromise of a device while its readable local database is accessible.
