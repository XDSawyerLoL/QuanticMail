# Quantic Identity Vault V0.8

V0.8 adds explicit identity backup and recovery without uploading private identity material to Quantic infrastructure.

## Goal

A Quantic identity must survive loss of the original browser or computer without turning Render into a custodian of private keys.

The V0.7 canonical identity is derived from the ECDSA P-256 signing public key. Therefore preserving the signing private key preserves the ability to prove ownership of exactly the same canonical address.

## Vault file

The exported file uses the `.quantic-vault` extension and contains a JSON envelope with:

- format/version metadata;
- PBKDF2-SHA-256 parameters and a random 128-bit salt;
- a random 96-bit AES-GCM IV;
- AES-256-GCM ciphertext.

The encrypted plaintext contains:

- human handle;
- ECDH P-256 encryption public/private JWKs;
- ECDSA P-256 signing public/private JWKs;
- original local identity creation date.

The current device authentication token is deliberately excluded.

## Password derivation

The browser derives the AES-256 vault key from the user password with PBKDF2-SHA-256 and 250,000 iterations. The vault format/version string is authenticated as AES-GCM additional authenticated data.

The password never leaves the browser and is not stored in the vault.

## Export flow

1. Read the current Quantic identity from IndexedDB.
2. Require an identity with V0.7 signing keys.
3. Require a password of at least 10 characters and a matching confirmation.
4. Serialize the identity keys locally.
5. Generate a random salt and IV.
6. Derive the AES key locally.
7. Encrypt with AES-256-GCM.
8. Trigger a local download of `<handle>-<fingerprint>.quantic-vault`.

No API call is needed for export.

## Restore flow

1. Start QuanticMail in a browser with no local identity.
2. Open `/vault`.
3. Select the `.quantic-vault` file and enter its password.
4. Validate the vault envelope and decrypt locally.
5. Validate the EC key material and recompute the canonical fingerprint from the signing public key.
6. Generate a fresh random device authentication token.
7. Store the restored identity in IndexedDB.
8. Return to QuanticMail.
9. QuanticMail performs the normal V0.7 proof-of-possession challenge with the restored signing private key and can therefore re-register the same canonical identity.

## Safety choices

- Restore never overwrites an identity already installed in the current browser.
- Vault files larger than 1 MB are rejected by the recovery UI.
- An incorrect password or modified ciphertext fails AES-GCM authentication.
- The canonical fingerprint is recomputed rather than trusted from the file name or unencrypted metadata.
- A fresh local auth token is generated after restore, so copying a vault does not preserve an old bearer token.

## Deliberate limitations

V0.8 is an **identity** backup, not a full mailbox backup. It does not contain:

- received messages;
- sent messages;
- contacts;
- pending outbox envelopes;
- delivery receipts.

Those remain local to the original browser in this version.

If the user loses both the local identity and all exported vault copies, Quantic Sillage cannot reconstruct the canonical identity. This is a consequence of the no-custody design, not a recoverable server-side account state.

## Future work

Potential next layers include an optional encrypted full-device backup, multiple-device authorization, key rotation certificates, recovery delegates, and peer-distributed identity records. None of those require changing the V0.8 vault's core rule: private keys are encrypted before leaving the user's device.
